# Native project-file implementation

This supplements the [selected design](project-file-design.md) and records the original qualification. See [current compatibility](../compatibility.md) for enabled profiles. The pure policy is accepted before file I/O changes: seven Lean properties, 53 authored vectors, 4,108 generated TypeScript comparisons and 28 malformed-wire pairs. The evidence is in `.audit/probes/windows-project-config/pure-acceptance.json`.

The [facade](../../src/installer/project/files/file.ts) owns target validation, platform dispatch, admission and text decoding. The [Linux backend](../../src/installer/project/files/posix.ts) retains the previous filesystem checks and publication behavior. The [shared Windows file service](../../src/internal/windows-files/managed.ts) now owns physical parent handles, native metadata, staging and publication. The public installer still calls the same two operations.

Publication uses `SetFileInformationByHandle` with `FileRenameInfo`. The created source handle stays open with delete access. The destination is the full Volume GUID path under the held physical parent directories; `RootDirectory` is null. `ReplaceIfExists` is false for an absent reviewed file and true for replacement. Microsoft documents those fields and the absolute-path form in [FILE_RENAME_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info). The backend checks the x64 structure layout before use.

The first native I/O probe reached publication after inspecting the staged bytes and metadata, then returned Win32 error 87 for a non-null `RootDirectory` and relative destination. That failed run and its source candidate are retained in `.audit/probes/windows-project-file-io/`. The full-path call is a separate candidate. Holding every physical ancestor without delete sharing keeps the reviewed path anchored while the source handle identifies the file being renamed.

Before publication starts, failure cleanup marks the created handle for deletion and closes it. That identifies the actual owned file without reopening its name. Once publication is attempted, an error retains the file for inspection; cleanup cannot accidentally delete a configuration whose rename may have succeeded. [SetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setfileinformationbyhandle) documents the rename and disposition classes and their access requirements.

The file reader uses the existing FileRead admission model and validates exact Volume GUID paths under held physical ancestors. DACL bytes are queried by handle, copied out of native allocation and released with the matching allocator. Existing DACLs must match the staged descriptor before configuration bytes are written. The file's admitted attributes and DACL digest are checked again before publication and through the published handle afterward. Extra streams and unsupported attributes remain refusals.

On the pinned Windows host, supplying an inherited descriptor to `CreateFileW` retained the DACL bytes but cleared `SE_DACL_AUTO_INHERITED`. Explicit `SetSecurityInfo` restored the exact source descriptor in the native premise probe. Replacement staging therefore requests `WRITE_DAC`, applies the reviewed DACL and its protected or unprotected state by handle, then keeps the full descriptor equality check before writing. It does not discard control bits or normalize access entries. The [setter documentation](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo) and [security-information flags](https://learn.microsoft.com/en-us/windows/win32/secauthz/security-information) describe that operation and its access requirements. The inherited premise is recorded in `.audit/probes/windows-project-file-security/`; the [file I/O acceptance](project-file-acceptance.md) also measures replacement under an explicitly protected DACL.

The Lean policy proves admission and review decisions. Linux file tests and five isolated Codex project lifecycle cases pass after the split. The Windows file I/O probe passes creation, replacement, permission and attribute preservation, stale review, read-only refusal and additional-stream refusal. A subsequent [Codex project pilot](windows-activation-acceptance.md#codex-project-scope) passes normal installation, replacement, replay, two-project discovery and removal. Process interruption and the remaining Windows release gates remain separate acceptance work. No Windows production profile is enabled; macOS qualification is deferred without a host.
