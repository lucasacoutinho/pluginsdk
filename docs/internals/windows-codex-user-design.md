# Windows Codex user installation

## Outcome and grounding

Qualify Codex 0.163.0 user installations on Windows x64 for `agent_plugins_v2`. This enables the existing `preview --target codex` workflow for basic skill, asset and remote HTTP MCP packages. The current Windows project profile remains unchanged.

The [normal SDK pilot](windows-activation-acceptance.md) already exercises this user scope. Production admission still requires its own interruption matrix and compiled command evidence. The ordinary recipe invokes native marketplace and plugin commands; the project recipe publishes a revision and edits project configuration. Their normal results do not establish each other's interruption behavior.

`InstallerEngineLive` owns the same reviewed lifecycle in both scopes. A user target holds the home installation lock. Windows commands retain each native writer before continuation. Recovery observes those retained births and settles the existing pending plan without executing its recipe again. The qualified [project recovery harness](windows-project-recovery-acceptance.md) supplies independent caller and worker admission, exact termination and closed-file observation boundaries.

User discovery differs from project discovery. Both projects must see the active user plugin. Both must lose it after removal. Native commands may rewrite the user's configuration, so acceptance preserves unrelated settings according to the observed native contract. It must not assume the project-file adapter's exact text and security guarantees apply to that native rewrite.

## Alternatives and decision

| Shape | Decision |
| --- | --- |
| Promote the user row from the earlier normal SDK run | Reject. It lacks the remaining interruption and compiled preview evidence. |
| Add a public platform override or user-specific installer service | Reject. Qualification does not need a new authority path or duplicate lifecycle. |
| Reuse the qualified recovery controls, then qualify compiled user commands and preview with the exact candidate row | Select. Existing interfaces and pure policies remain authoritative. |

The candidate adds one row: host `codex`, platform `win32`, version `0.163.0`, scope `user`, revision `codex-local-marketplace:1`, format `agent_plugins_v2`. Compatibility N1–N8 must agree with the Lean oracle before the isolated profile overlay is prepared. Other rows retain their current behavior.

## Private interfaces and sequence

The recovery fixture keeps the established private interface: create an isolated case, build a pinned generation, capture a closed journal, discover the active package, verify approved payload bytes and check unrelated state. Its destination is `user`; it introduces no project configuration capture or second project lock. Case definitions remain the seven existing cuts: before and after install, replacement and removal, plus worker completion after caller termination.

The SDK recovery copy receives three reversible overlays: the exact candidate row, the two established engine checkpoints, and standard Effect worker tracing. Process-control and checkpoint support come from the current sealed qualification. Each case must finish exact caller, worker and retained native-writer checks before any full inventory or subsequent case. Every case needs independent acceptance before cleanup.

Compiled normal commands use a separate source snapshot with only the candidate row and standard tracing. Engine pause hooks do not belong in that command snapshot. Compilation includes the dynamically selected `.js` worker, JSON schemas and pinned package metadata. The normal command scenario covers build, plan, show, apply, replacement, removal, unchanged planning and completed replay.

Preview needs a separate bounded scenario on one stable source directory. It must install a derived development identity, report unchanged without another execution, replace changed source under that same identity, remove it, and report unchanged removal. The caller must use only `preview --target codex` and the existing definition. A preview can create a planning worker and an applying worker; completion accounting must cover both before reading their diagnostics.

Only the exact qualified profile bytes are promoted after all required native cases, independent validation, evidence retention and owned-stage cleanup. Production models, worker protocol and authoring schemas remain unchanged unless a retained counterexample requires a separate LDD change.

## Acceptance limits

Acceptance requires exact approved bundles, valid plan commitments, native discovery in both projects, preserved unrelated state, one execution per actual change, zero execution during replay or unchanged results, and removal of the owned native entries. Job accounting remains secondary to exact process completion evidence. Unknown completion prevents inventory, cleanup, retries and stage reuse.

This does not qualify other Windows versions or formats, Claude Code, bundled stdio, hooks or agents. macOS, third-party authentication, Grok native testing, CI, package-consumer and release-wide checks retain their existing deferrals.
