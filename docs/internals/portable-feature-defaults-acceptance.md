# Portable feature build defaults

Normal `pluginsdk build` now selects portable v2 when a definition contains hooks or agents. The same definition produces Claude and Codex packages for the qualified Linux and Windows user profiles. Stdio-only definitions keep portable v1; basic definitions keep their existing formats. Explicit older formats remain available.

The [design](portable-feature-defaults-design.md) retains the existing definition, build and preview interfaces. There is no new author wrapper, platform branch or portable-mode flag. Preview calls the same proved recommendation function as build.

## Proof before integration

The existing `BuildFormat` input remains the client and three Boolean feature facts. BF1 and BF2 now require the client-specific portable v2 format for agents or hooks. BF3 retains the stdio-only result; BF4 retains the basic result. Proof bodies, strict wire and input schemas keep their existing interfaces.

The isolated candidate first proves all four obligations and matches all sixteen finite inputs with independently derived expectations. Both authoritative decoders reject the original 33 malformed requests. Main reviews and recompiles those proofs, checks their axioms, reruns conformance and preserves the exact dependency bytes before root build output changes.

Root integration then rebuilds Lean, checks **318/318 property proofs**, rebuilds the oracle and passes the sixteen-case TypeScript/oracle comparison and 33 malformed refusals. Profiles and runtime retain their previous hashes until that pure gate passes. No property or public schema is added; two existing property expectations change.

All four complete bundles and their 64 payload-file observations equal the exact native-qualified fixtures. Each contains its expected skill, MCP server, both hooks, agent document, three admitted process descriptors and one shared runtime. The captured builds also pass the production `readBuild` operation with their real definitions. All frozen source files stay unchanged.

## Scoped checks and corrections

Strict TypeScript checking, Effect diagnostics on ten scoped files, lint and all 31 retained tests across seven scoped suites pass. The checks cover format selection, feature projection, exact profile admission, complete v2 packages and refusal cases, v1 compatibility, portable formats and preview boundaries. CI, package-consumer and release-wide suites are not run.

The first scoped run exposes the old compiler-stage assertion that every v2 profile must remain unqualified. That temporary guard belongs to the earlier compiler-only checkpoint. Its support-bound contract now lives at the profile owner, which admits the four evidenced tuples and refuses other registered queries. The compiler's seven package, validation and local-runtime tests remain. Only the two affected suites and changed-test static checks are rerun after that correction.

Two qualification-script errors are retained separately. One lookup omitted platform and compared a Windows row with a Linux row; it now compares all identity fields. The other called `readBuild` without its required definition argument after a successful CLI build. Corrected verification uses the real definition and fresh output paths. Neither correction changes product code or native evidence.

The evidence is under `.audit/probes/portable-features-defaults/`: baseline and before images, private and root proof receipts, frozen proof dependencies, scoped logs, test-audit decision, exact profile and emitted-code comparisons, CLI builds and main verification. `acceptance.json` seals those records and explicitly preserves every superseded predecessor file.

## Remaining scope

The [user compatibility reference](../compatibility.md) and [authoring guide](../authoring.md) describe the enabled workflow and process requirements. Project-scope stdio, hooks and agents, source symbolic-link qualification, additional client adapters and broader release acceptance remain open. Backend tool authorization remains separate from native agent shell policy.

No macOS host is available, so its qualification remains deferred. Grok native tests, third-party authentication, CI, package-consumer checks and publication remain deferred. The package and repository remain private; this checkpoint performs no external publication or deployment.
